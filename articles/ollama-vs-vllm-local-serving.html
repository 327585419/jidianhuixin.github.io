Ollama 和 vLLM 怎么选？本地部署推理框架对比

发布：2026-10-12 分类：部署实操 阅读约 8 分钟

结论先行：一句话：个人本机、单用户、想快速跑起来，用 Ollama；多用户对外服务、要并发吞吐，用 vLLM。

先给结论：谁用、怎么用，决定选哪个

一句话：个人本机、单用户、想快速跑起来，用 Ollama；多用户对外服务、要并发吞吐，用 vLLM。

这不是偏好问题，是架构问题。Ollama 把模型下载、量化、加载、API 全包了，一条命令就能对话，代价是并发能力弱、显存调度粗放。vLLM 的核心是 PagedAttention 和 continuous batching，专为"很多人同时打请求"设计，但部署门槛高，单用户闲聊时你根本吃不到它的优势。

中间还有一层：单用户但追求极致速度，可以看 llama.cpp 系列（Ollama 底层也是它）；团队内部三五个人轻量共享，Ollama 加个反向代理也能凑合，只是并发一上来就露怯。

Ollama 的优势：开箱即用和 GGUF 生态

Ollama 最值钱的地方是"省事"：

  • 模型管理像 Docker：ollama pull、ollama run，模型、标签、版本一目了然，不用自己写加载脚本。
  • GGUF 量化生态成熟：Q4_K_M、Q5_K_M、Q8_0 这些量化档位覆盖从"能跑"到"接近原精度"的全区间，24GB 显存的 4090 能塞下比 FP16 大得多的模型。
  • CPU/GPU 混合推理：显存不够时自动往内存和 CPU 卸载，虽然慢，但至少能跑起来。
  • 自带 OpenAI 兼容接口：/v1/chat/completions 直接可用，接 LangChain、Dify、Open WebUI 都顺。

短板也明确：并发调度简单，多请求排队时吞吐上不去；长上下文显存浪费明显。它适合"一个人、一台机器、一个模型"。

vLLM 的优势：显存利用和并发吞吐

vLLM 解决的是 Ollama 解决不了的问题：

  • PagedAttention：把 KV Cache 按页管理，显存碎片大幅减少，同样显存能塞下更多并发序列。官方口径下显存利用率可显著提升，具体倍数需按模型和序列长度实测。
  • Continuous batching：请求不等整批结束，谁先完成谁先出，GPU 空转时间大幅压缩。这是吞吐量差距的主要来源。
  • OpenAI 兼容 API：vllm serve 起服务，接口规范，方便对接生产系统。
  • 张量并行：多卡切分模型，1~8 卡都能配。

代价是：对软件版本敏感，对 GPU 架构有要求。V100 是 sm_70（Volta, 2017），主流新版 PyTorch/vLLM 已逐步淡化对 sm_70 的官方支持，能不能跑、跑哪个版本，部署前必须实测确认。A100（sm_80）支持 BF16、TF32、MIG，是当前私有化部署更稳的选择。

并发压测：盯住三个指标

别信"感觉挺快"，要压测。三个指标：

指标含义怎么看
TTFT（首字延迟）从发请求到吐出第一个 token决定"跟不跟手"，对话场景最关键
总吞吐（tokens/s）单位时间所有请求合计产出决定能扛多少并发用户
显存占用峰值显存与 KV Cache 占比决定并发上限和会不会 OOM

做法：用固定长度输入、固定输出长度，并发从 1 逐步加到 8、16、32，记录三个指标的变化曲线。Ollama 通常在并发 4~8 时吞吐就见顶，vLLM 能拉得更高，但具体拐点取决于模型大小、量化方式和卡型，需实测确认。别拿别人的跑分套自己的场景。

硬件怎么配：显存先算够，再谈框架优化

顺序不能反：先算显存够不够，再选框架。 显存不够，PagedAttention 也救不了你。

粗略估算：FP16 下，模型权重约占"参数量 × 2GB"。7B 约 14GB，13B 约 26GB，70B 约 140GB。再叠加 KV Cache 和激活值，实际要留 20%~40% 余量。量化能压缩权重，但 KV Cache 仍吃显存。

结论/建议

  • 一个人一台机：Ollama，省心，够用。
  • 要速度的单用户：llama.cpp 系列调参，或直接上 vLLM 单实例。
  • 团队内部轻量共享：Ollama + Nginx 反向代理，先跑起来，并发上来再换。
  • 对外服务、多用户：vLLM，配 A100；V100 要提前实测版本兼容性。
  • 硬件决策：先把显存算够，再谈框架优化。V100 便宜但生态在退坡，A100 贵但省心，4090 适合个人不适合生产。
